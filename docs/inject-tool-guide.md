# 灌流调试工具 · 接入与使用

面向已接入 AI 录音 Native 能力的 Android 工程。本文覆盖两件事：

1. 如何依赖 `ai_voice` 组件并进入调试页；
2. 如何用灌流工具做单次验证与批量 WER 测试。

依赖配置见 [`nativesdk-dependency-guide.md`](./nativesdk-dependency-guide.md)，
接口文档见 [`modules/README.md`](./modules/README.md)。

---

## 一、灌流是什么

用本地音频文件替换麦克风采集数据，让 ASR / 翻译链路跑在**可复现的输入**上。

真人对着麦克风念一遍，每次的音量、语速、环境噪声都不同，结果无法比对；灌一个固定文件进去，
才谈得上「这次改动让识别变好了还是变差了」。

**三条硬约束，不满足就没有任何输出：**

| 约束 | 说明 |
|---|---|
| 只作用于手机 MIC 通道 | 底层只有 `PhoneMicAudioInputFactory` 这条路支持灌流，蓝牙耳机通道是另一个实现，设置对它完全无效 |
| 只支持整型 PCM 的 WAV | 16kHz / 单声道 / 16bit，`audioFormat=1`。非 PCM 的表现是「灌流在跑，但一条 ASR 都没有」，不报错也不崩溃 |
| 只在下次开始录音时生效 | 配置在录音任务创建音频输入的那一刻被读取，录音中改配置对本次录音没有影响 |

音频格式转换：

```bash
ffmpeg -i 输入.wav -ar 16000 -ac 1 -c:a pcm_s16le 输出.wav
```

## 二、依赖与进入方式

### 2.1 依赖（本地 aar）

把提供给你的 `ai_voice-release.aar` 放进工程的 `app/libs/` 目录：

```
app/
└── libs/
    └── ai_voice-release.aar
```

在 `app/build.gradle` 中声明：

```gradle
android {
    // ...
}

dependencies {
    implementation files('libs/ai_voice-release.aar')
    // 其余 SDK 依赖见 nativesdk-dependency-guide.md
}
```

> 若使用 `flatDir` 方式，在根 `build.gradle` 的 `repositories` 中加
> `flatDir { dirs 'libs' }`，再用 `implementation(name: 'ai_voice-release', ext: 'aar')`。
> 两种写法效果一致，`files()` 更直接。

⚠️ **aar 不携带传递依赖**。源码工程里 `ai_voice` 是用 `api` 把 `thingsmart`、
`thingsmart-bizbundle-wearkit`、`thingsmart-bizbundle-panelmore`、`thingsmart-bizbundle-family`
传下去的，打成 aar 后这层传递会丢失，**这些依赖必须在你自己的 `build.gradle` 里显式声明**，
版本与配置照 [`nativesdk-dependency-guide.md`](./nativesdk-dependency-guide.md) 写。
缺哪个会在运行时报 `ClassNotFoundException` 或 `NoClassDefFoundError`。

⚠️ **本组件依赖家庭能力**：`AbsBizBundleFamilyService` + `ThingHomeSdk` 被用于设备下拉与录音详情，
因此除了 Native 接口外，你的工程还必须完成**登录**与**家庭初始化**，否则部分页面会取不到数据。

### 2.2 进入方式

所有调试页都收敛在一个总入口 `NativeEntryActivity`，从你自己的代码里拉起：

```java
import com.tuya.smart.ai_voice.nativeui.NativeEntryActivity;

// 在你的调试菜单、长按彩蛋、或任意入口按钮里
NativeEntryActivity.start(context);
```

允许传 Application / Service 等非 Activity 的 Context，内部会补 `FLAG_ACTIVITY_NEW_TASK`，
不需要你自己处理 flag。

进入后是一张能力清单，灌流相关的两条在最下方，标注「调试」。

> **发布前请移除对本组件的依赖**，避免调试页随正式包一起发出去。

## 三、单次灌流（快速验证）

**用途**：确认灌流链路通不通、某个音频能不能被识别。

**入口**：总入口 →「灌流设置（调试工具）」，或 Native 录音页右上角的齿轮图标。

**步骤**

1. 打开「开启灌流」；
2. 选一个音频（单选，SDK 只接受一个文件名）；
3. 保存 → 回到 Native 录音页 → 开始录音。

录音页顶部会常驻一条**灌流模式横幅**，显示当前灌的是哪个文件。这条横幅是刻意做的：
开着灌流时波形和转写全部来自文件、与麦克风无关，不明说的话第一反应会是「SDK 有问题」。

**灌流播完会自动停止录音**，并 toast 说明原因。

### 3.1 在你自己的业务里生效

灌流配置是**全局的**，写在 SDK 的内存里，不绑定任何页面。也就是说：

> **在这个设置页开启灌流后，回到你自己的业务代码里调 `startAudioRecording` 开始录音，
> 灌流同样生效**——采集到的不是麦克风的声音，而是你选中的那个音频文件。

这是验证「自己的录音链路接得对不对」最省事的办法：不用对着麦克风念，
用一段固定音频反复跑自己的业务流程，转写结果每次都应该一致。

前提仍是那三条约束——走手机 MIC 通道（`audioSource` 为系统麦克风 16K 单声道）、
整型 PCM 的 WAV、且配置要在 `startAudioRecording` **之前**下发。

⚠️ 反过来说，**忘了关就是个坑**：灌流开着的时候，你业务里所有走手机 MIC 的录音
都会被替换成文件，且除了本 Demo 的录音页会显示横幅外，你自己的页面不会有任何提示。
用完请回设置页关闭，或重启进程（配置不持久化）。

**几个要点**

- 配置写在 SDK 的内存字段里，**不做本地持久化，进程重启即失效**。这是有意为之：调试开关被持久化后
  「重启后还开着但没人记得」是最常见的事故。
- 选中的设备不是「手机本地录音」时，设置页顶部会给出红色提示——设置对该设备不生效。
- 关闭灌流即恢复真实麦克风采集，已落地的音频文件不删除。

## 四、批量测试（WER 评测）

**用途**：多轮跑批、自动算 WER、导出报告，用于回归与版本间比对。

**入口**：总入口 →「灌流批量测试（调试）」。

### 4.1 准备语料

三类文件都放在 `ai_voice/src/main/assets/audio_inject/`：

```
ai_voice/src/main/assets/audio_inject/
├── manifest.json          清单，为每个音频提供源语言与能力开关
├── zh_meeting_01.wav      音频，16kHz / 单声道 / 16bit 整型 PCM
├── zh_meeting_01.txt      参考答案，UTF-8，建议每行一句
├── de_lecture_01.wav
└── de_lecture_01.txt
```

`manifest.json` 是**裸数组**：

```json
[
  {
    "name": "zh_meeting_01.wav",
    "originalLanguage": "zh"
  },
  {
    "name": "de_lecture_01.wav",
    "originalLanguage": "de",
    "targetLanguage": "en",
    "needTts": false
  }
]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 与 wav 文件名完全一致 |
| `originalLanguage` | 是 | 源语言，ASR 用 |
| `targetLanguage` | 否 | **只能填一个**（底层一次录音只支持一个目标语言）；留空表示不翻译 |
| `enableRealtimeTranscription` | 否 | **默认 `true`** |
| `enableRealtimeTranslation` | 否 | **默认 `true`**，但没填 `targetLanguage` 时自然不会生效 |
| `needTts` | 否 | **默认 `true`**，仅在实际发生翻译时才有意义。把译文合成语音播回，无法自动评分，只在报告里记录开关状态供解释耗时 |

> 三个布尔字段**缺省一律为开**：写进清单的音频就是要完整跑一遍，缺省关掉反而会让人以为
> 「配了却没生效」。要关某一项就显式写 `false`。

**三条关联规则**

- 清单里**没有条目的音频不能参与跑批**——源语言只能来自清单，猜错会让整轮数据不可信。
  这类文件在列表里会置灰并标注原因，但仍可在「灌流设置」页做单次灌流。
- **没有同名 txt** 的音频照常跑，只是不算 WER，报告里会写明。
- 非整型 PCM 的音频**直接拦截**；采样率 / 声道 / 位深不符的给橙色警告，可以选择「仍然开始」。

### 4.2 跑批

1. 勾选音频（可多选）；
2. 填重复次数（1~99）；
3. 「开始跑批」。

总轮数 = 选中音频数 × 重复次数，顺序是**文件外层、重复内层**——同一文件的多次重复在时间上连续，
观察抖动时不会被别的语料插进来干扰。

跑批期间界面上有：进度（`文件 · 第 N/M 次 · 总 X/Y 轮`）、当前阶段、实时转写滚动文本、
以及边跑边出的轮次结果列表。**结果列表是边跑边刷的**，十几轮跑到一半发现 WER 全是 100%，
可以立刻掐掉去查格式，不必等一小时。

**跑批期间屏幕保持常亮，退出页面即中止**（不做后台化）。中止时当前轮记为失败，已完成的轮次照常出报告。

### 4.3 一轮的流程与超时

```
下发灌流配置 → 开始录音 → 等灌流播完 → 停止录音 → 等录音结束事件
  → 拉取转写结果 → 计算 WER → 下一轮
```

任一环节卡住由**单轮总超时**兜底：`音频时长 × 3 + 60 秒`。超时判该轮失败并**继续下一轮**——
跑批的价值在于无人值守，一轮卡住就全盘中止等于白跑一夜。

轮与轮之间间隔 1.5 秒，给底层留出释放音频通道的时间。

失败轮会保留在报告里并标出具体原因（超时 / 无识别结果 / 接口报错），
连续多轮无结果通常意味着音频格式不对，而不是识别能力差。

### 4.4 报告

跑完后产出三份文件，都在应用私有目录：

```
<外部私有目录>/Documents/inject_report/
├── inject_report_<批次ID>.html    本次跑批的完整报告
├── inject_<批次ID>.csv            本次每轮一行
└── inject_history.csv             累积 CSV，跨跑批追加
```

点「分享报告」可把 HTML 通过系统分享面板发出去（走 FileProvider，不需要任何存储权限）。

**HTML 报告**包含：总体 KPI（准确率 / WER / 参考词数 / 错误合计 / 总耗时）、错误构成 S/D/I 占比条、
轮次概览表、每轮的测试条件与逐句对比、全文逐词对比（替换标红并悬停显示应为何词、插入标黄、删除标绿）、
归一化后的文本、识别原文与译文、以及「计算方式」章节。支持深色模式，单文件无外部依赖。

**累积 CSV** 是看趋势用的，同时充当持久化（本模块没有数据库）。字段：

```
batchId, time, file, repeat, repeatTotal, sourceLang, targetLang, tts, status,
N, S, D, I, wer, accuracy, durationMs, recordId
```

同一个音频在历次跑批里的 WER 走势，直接筛 `file` 列即可。

## 五、WER 口径

```
WER = (S + D + I) / N        准确率 = 1 − WER（下限截到 0）
```

S 替换、D 删除（参考有但没识别出来）、I 插入（识别多出来的）、N 参考词数。
总体 WER 按**词数加权**汇总，不是各轮 WER 的算术平均——长音频的权重本就该更高。

**归一化**（参考答案与识别结果套用同一套规则）：

1. 统一转小写、去首尾空白；
2. 剔除语气词 `啊额呃嗯唉哎哦喔呵哈儿`；
3. 中文逐字切分，英文等按词切分；
4. 标点**替换为空格**而非删除——直接删会把 `starkes.Kulturellen` 粘成一个词，凭空制造错误；
5. 千分位还原：`40 000` → `40000`；
6. 数词归一化：`two` / `zwei` → `2`。

**对齐**：Levenshtein 动态规划 + 回溯，代价相同时优先判替换、其次删除。

**逐句对比**：把识别分段单调切分后分配给参考行，使各行编辑距离之和最小。
**固有限制**：一个识别分段不会被拆开分配给多个参考行，ASR 把多行参考合并成一段输出时，
必然有参考行分不到内容而被判漏识，属于对齐口径造成的虚高——报告在这种情况下会显示醒目告警。
**全文 WER 不受此影响，任何情况下都以全文口径为准。**
想要准确的逐句结果，请让参考答案的分行与音频中的自然停顿一致。

> 本实现与 iOS 端 `PerfusionWERCalculator` 逐行对齐，两端结果应当一致。
> 修改任何一条归一化规则或对齐策略前，必须确认 iOS 侧同步修改。

## 六、排查

| 现象 | 原因与处理 |
|---|---|
| 灌流在跑，但一条 ASR 都没有 | 音频不是整型 PCM。批量页会提前拦截并给出转换命令；单次灌流页不拦，需自查 |
| 结果行显示「未拿到 recordId」 | 录音任务没建起来。检查登录态（`startAudioRecording` 依赖账号 token）与麦克风权限 |
| 结果行显示「一条识别结果都没有」但实时转写有文字 | 实时推送与查表是两条通道。已对 recordId 的三种写法做了兼容尝试；若仍为空，多半是拉取时机早于后端落库 |
| WER 明显虚高 | 看报告里「归一化后文本 · 识别」是否有重复内容；再看逐句对比上方有没有「识别分段数少于参考行数」的告警 |
| 每轮都跑到超时才结束 | 灌流结束回调没触发，检查音频是否真的被读完 |
| 跑完批之后正常录音还在灌文件 | 不应发生（页面销毁时会清配置）。手动进「灌流设置」关闭一次即可 |

## 七、已知限制

1. **参考答案与清单只在 assets**，改动需要重新编包。语料要频繁校准时这个循环较难受——
   可改为「目标目录优先、assets 兜底」，改动约 30 行。
2. **拉取转写结果只拉一次，不轮询**。若后端落库慢于录音结束事件，会拿到不完整的文本。
3. **目标语言只能一个**，多语言需分批跑。
4. **TTS 不评分**，只在报告里记录开关状态。
5. **译文不评分**，只记录原文供人工查看——WER 对翻译不是合适的指标。
6. **aar 不携带传递依赖**，SDK 与 bizbundle 需在你的工程里显式声明，见 2.1。
